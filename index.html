Day 0 infrastructure

Bootstrapping Azure Terraform state

Jon Abbott

The problem

  • Terraform needs a remote backend for state and locking
  • Azure Storage is the usual host — but something must create it first
  • The primary Terraform config cannot create its own backend
  • Manual Portal clicks or one-off scripts invite drift and risk
This is the classic Day 0 chicken-and-egg: Terraform should manage infrastructure declaratively, yet it depends on state storage that does not yet exist. Historically teams papered over this with ad-hoc setup, which does not scale across environments.

Challenges & requirements

  • Fully automate backend resource creation
  • Minimise manual intervention
  • Repeat deployments across environments and subscriptions
  • Stay aligned with IaC and run inside CI/CD
  • Prefer native Azure tooling where possible
Bootstrap resources stay separate from the main Terraform configuration: resource group, storage account, blob container, and diagnostics — provisioned before any Terraform apply.

Options considered

Portal

Works with

  • Quick PoCs
  • No extra tooling

Watch for

  • Not repeatable
  • Hard to audit
  • Config drift
Azure CLI

Works with

  • CI/CD scripts
  • Familiar ops

Watch for

  • Imperative
  • Custom idempotency
  • Harder to maintain
ARM

Works with

  • Native Azure
  • Declarative

Watch for

  • Verbose JSON
  • Hard to author
  • Superseded by Bicep
Bicep

Works with

  • Declarative IaC
  • CI/CD pipelines
  • Idempotent deploys

Watch for

  • Second IaC language
  • Separate bootstrap repo
Portal is only for experiments. CLI is pragmatic but diverges from IaC. ARM is viable but not preferred for new work. Bicep gives the best balance of automation, maintainability, and Azure-native support.

Decision: bootstrap with Bicep

  • Dedicated subscription-scoped Bicep deploy runs before Terraform
  • Creates the house: RG, storage, networking, diagnostics, RBAC
  • Terraform configs assume the backend already exists
  • Main Terraform never creates or manages bootstrap resources
Keep bootstrap scope intentionally small. Store templates alongside platform repos, version them through CI/CD, and document execution as part of environment provisioning.

Advantages of Bicep bootstrap

  • Fully automated Day 0 infrastructure
  • Repeatable across environments and subscriptions
  • Aligns with Infrastructure as Code practices
  • Azure-native, idempotent, CI/CD friendly
  • Trade-off: maintain Bicep and Terraform side by side
Risks: bootstrap becomes a special-case path; backend architecture changes need template and pipeline updates. Mitigate by keeping scope small and testing templates in CI.
Hybrid model: Bicep is stateless and builds the house. Terraform is stateful and moves in, storing state in the bootstrapped storage. Typical flow: deploy Bicep, unlock or reach storage privately, run Terraform, return storage to a hardened resting state.

What Bicep provisions

  • Resource group for state storage
  • VNet, subnet, NSG, private endpoint, and private DNS
  • Zone-redundant storage account and tfstate container
  • Log Analytics workspace and blob diagnostics
  • Entra ID RBAC for the pipeline identity
Role assignment uses the Storage Blob Data Contributor GUID (ba92f5b4-2d11-453d-a403-e96b0029c9fe) for immutability and localisation safety. Deployer needs Owner or User Access Administrator at subscription scope.

Hardened by default

  • Shared key access disabled — Entra ID only
  • Public network access disabled — private endpoint only
  • TLS 1.2 and HTTPS-only transit
  • Blob versioning and 14-day soft delete
  • Diagnostics to Log Analytics for audit
  • SKU: Standard_ZRS
  • Default network action: Deny
  • No public blob access
  • NSG deny-all inbound on the state subnet
  • Allow ~5 minutes for RBAC to sync
Zero-trust resting state: keys off, public access off, private endpoint and DNS for blob. Soft delete and versioning protect against accidental state loss.

Pipeline access to state

  • Hosted runners cannot reach a private-endpoint-only account
  • Prefer self-hosted agents inside the VNet (or peered)
  • Or temporarily unlock / whitelist the runner IP, then re-lock
  • Set BOOTSTRAP_TF=false to skip redeploy once live
Re-running Bicep every pipeline can add 3+ minutes. After the backend exists, skip bootstrap and still extract backend parameters for init. Dynamic firewall whitelisting needs storage write permissions and briefly opens a pinhole.

Implementation


              az deployment sub create \
                --location uksouth \
                --template-file bicep/main.bicep \
                --parameters bicep/environments/development.params.json \
                --parameters workflowPrincipalId=<PIPELINE_SP_OID>

              # terraform {
              #   backend "azurerm" {
              #     resource_group_name  = "…-rg-uks-terraform"
              #     storage_account_name = "…tfstatestorage"
              #     container_name       = "tfstate"
              #     key                  = "dev.terraform.tfstate"
              #     use_azuread_auth     = true
              #   }
              # }
Pass the pipeline service principal or managed identity object ID so Bicep can grant Storage Blob Data Contributor. Storage account names must be globally unique; confirm the region supports ZRS.
